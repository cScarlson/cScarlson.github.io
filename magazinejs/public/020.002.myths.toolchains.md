
Frontend Toolchain Myths
================================================================
This article elucidates many of the myths you likely presumed when this book caught your eye. While you _can_ skip this part of the book and go straight to the patterns & approaches catalog, you still may want to circle back around to this part of the book, if only to ensure you truly understand _why_ these are addressed as myths. ## Reactive Data

### Myth
_You need a library like RxJS, Signals, or otherwise to have Reactive Data_.

### Reason
Data Reactivity can be accomplished in roughly 25 LOC using _The Observer Pattern_.

### The Observer Pattern
Rather than pulling in RxJS (or similar), you may just have one small area of the code that needs some reactivity. RxJS _says_ it is a new and improved version of _The Observer Pattern_. However, you might say it is more so just _inspired_ by The Observer Pattern as it has little alignment with the pattern's actual interface. The only thing RxJS and The Observer Pattern really have in common is _reactivity_ and calling things a "Subject". When all you need is that, you may be better off writing a _Subject_, the main participant of The Observer Pattern.


#### To Spec

##### `@core/utilities/patterns/behavioral/observer.ts`
```typescript
interface IObserver {
    update(state: any);
}

class Subject {
    state: any = null;
    observers: Set<IObserver> = [ ];
    
    constructor(state: any = this.state) {
        this.state = state;
    }
    
    attach(observer: IObserver) {
        this.observers.push(observer);
    }
    
    detach(observer: IObserver) {
        for (let i = this.observers.length; i--;) if (this.observers[i] === observer) this.observers.splice(i, 1);
    }
    
    notify() {
        for (let observer of this.observers) observer.update(this.state);
    }
    
}

export type { IObserver };
export { Subject };
```

That is basically it for The Observer Pattern. You have a structure that accepts "observers". Observers are just objects with an `update` method. The `Subject` calls its `notify` method whenever its `state` changes. Observers can detach themselves for cleanup and we iterate backward in the `detach` method to not modify the `observers` collection in place while we `splice` them out. That said, here are the deviations from the pattern that reflect how I like to write my Subject class so that anything can extend it and provide more flexibility for Observers.

#### Recommended Deviations from The Spec

##### `@core/utilities/patterns/behavioral/observer.ts`
```typescript
interface IObserver {
    call(state: any);  // use `call` instead of `update`. allows us to invoke functions or objects with a `call` method.
}

class Subject {
    ['undefined']: any = null;
    observers: Set<IObserver> = new Set();  // use JS Set
    
    constructor(state: any, private __key__: string|undefined) {  // allow 'key' for targeting which variable is of interest
        this[__key__] = state;  // set whichever variable reflects subject's state
    }
    
    attach(observer: IObserver, notify: boolean = true): Subject {  // use notify flag for automatically providing current state
        const { state, observers } = this;
        
        observers.add(observer);
        if (notify) observer.call(state, state);  // notify observer as soon as attached
        
        return this;
    }
    
    detach(observer: IObserver): Subject {
        const { observers } = this;
        observers.delete(observer);
        return this;
    }
    
    notify(state: any = this[this.__key__]): Subject {  // use default with ability to override
        const { observers } = this;
        observers.forEach( observer => observer.call(state, state) );  // use `call` instead of `update`
        return this;
    }
    
}

export type { IObserver };
export { Subject };
```

##### `**/observer.class.ts`
```typescript
import { type IObserver, Subject } from '@core/utilities/patterns/behavioral/observer';
import { store } from '@core/store';

class ObserverClass implements IObserver {
    data: Subject = new Subject({}, 'state');
    
    constructor(...) {
        this.data.attach(this);
        this.data.state.x = 'test';
        this.data.notify();
    }
    
    call(state: unknown) { ... }
    
}
```

##### `**/observer.function.ts`
```typescript
import { store } from '@core/store';

function handleStateChange(state: unknown) { ... }

store.attach(handleStateChange);
```

### Synopsis
As you'll notice, we can use both `function`s _and_ `class`es as our observers because we deviated a little bit from The Observer Pattern to look for a `call` method instead of an `update` method, which `function`s naturally have. We also added a `notify` flag to the `attach` method to control whether or not the observer should be automatically invoked when attached. Moreover, we made `Subject` more extensible by giving subclasses the ability to configure which _key_ should be used to store the subject's _state_ rather than being married to only using a variable called "`state`"; in face, if the entire state should be `this` then we can use a simple getter operation such as `get someKey() { return this }`. With only about 25 LOC (lines of code) we instantly breathed _reactivity_ into our app with full control over its maintenance and evolution. I encourage you to implement "observables" in this way next time you need a little reactivity in your app. Maybe the evolution of _your_ Subject will become the next most-downloaded reactive library on NPM. In an article coming up, we demonstrate why you may not need to always spring for a library like Redux, Zustand, NgRX, or other State Management libraries.



## Reactive Store

### Myth
_You need a library like Redux, Zustand or similar to have a Reactive Store_.

### Reason
A Reactive Store can be accomplished in roughly 25 LOC using a `Subject` from _The Observer Pattern_.

### Synopsis
By creating a store in about 15 LOC (Lines Of Code) that extends a `Subject`, and leveraging a Reducer that is about 5 LOC, we accomplished a Reactive State Store that is reusable across any domain. In fact, we even leverage the Reducer's `execute` method to override it for specific needs. For now, we spare you from some of the implementation details which we describe intimately in an article coming up that exists as a formal, Gang of Four style Software Design Pattern specification



## Side Effects & Mediation

### Myth
_You need a library like Redux Saga, Thunk, or otherwise to handle Side Effects_.

### Reason
What you want is _mediation_ (see The Mediator Pattern) and oftentimes a simple wrapper function will suffice.

#### React Mediator Example
```typescript
import React, { createContext, useReducer, Dispatch } from 'react';
import { reducer } from './reducer';
import { user as $user } from '**/services';

const DEFAULT_STATE = { ... };
const Context = createContext(DEFAULT_STATE);

function useMediator() {
    const [ state, dispatch ] = useReducer(reducer, DEFAULT_STATE, state => state);  // todo: run through middleware
    const mediator = mediate({ state, dispatch });
    return mediator;
}

function mediate({ state, dispatch }) {
    const token = '';
    
    return async function publish(action) {
        const { type, payload } = action;
        
        switch (type) {
            case 'TOKEN:FOUND':
                token = payload;  // set in memory here. keep protected.
                return;  // do nothing
            case 'USER:SETTINGS:CHANGED':
                const response = await $user.settings.update(payload, { token });  // make an async call before hitting reducer
                return dispatch({ ...action, payload: response });  // replace payload
            default: return dispatch(action);
        }
    };
}

export { DEFAULT_STATE, Context };
export { useMediator };
```

#### Standard Event-Driven Mediation
Every app should leverage an _Application Head_ of some kind. This absorbs complexity throughout the rest of the system, allowing subdomains to remain lightweight & portable. Using a standard [Event-Driven] mediator not only is the best way to handle side effects but also allows developers to write their own _CELs_ (_Custom Event Loops_). By interjecting on the dispatch and running it through an _Interjection Handler_, the handler can then make roundtrips to the server before storing the response data in a store and then continuing the Event Loop on the same channel. This makes it possible, for example, for a UI component to listen on the same channel that a Call To Action uses to dispatch an ID before the listener gets back hydrated data that actually originated from the server. When reading the GoF pattern in the "Custom Event Loop" article coming up, keep in mind that minor pieces of boilerplate can be reduced by leaning the pattern more toward the version of the Publish-Subscribe pattern that extends the `EventTarget` you see in the article, "The Reactive Store Pattern", under "_Using an `EventTarget` for The Publish-Subscribe Pattern_".

#### Defining Channels
The recommended anatomy of a channels docket is this.
- An object that maps an interface key, the _Channel Key_, to a _Channel Value_.
- Channel Key: A fully-qualified, uppercase, colon-delimited object key made of nouns and one verb.
  - Starts at the root domain.
  - Indefinitely narrows down the scope in subdomains.
  - Ends with a verb in one or more conjugations, preferably the same one, usually past tense or a _Derivational Suffix_ ('tion, 'sion, etc). Examples for such suffixes are
    - `...:SELECTION`
    - `...:REVISION`
    - Derivational Suffixes can also precede a past tense conjugate when necessary.
 - Channel Value: a URL-looking value that starts with a domain-id and a pathname that begins with the verb used in the key, with all subdomains as segments of the pathname thereafter.
   - All text is typically lowercase.
   - Having URL-like Channel Values allows you to scale toward more performant subscriptions that allow for higher or lower domains to be subscribed to.

### Synopsis
As you can see, all we need to do is wrap our `dispatch` function and we save ourselves from pulling in external dependencies. There really is no need for most applications — even at scale — to pull in something that you don't have control over that, as you'll see, also doesn't do much to require it as a 3rd-party package in the first place. Later on you can break this out into different Contexts; ones that might even inherit some of the behavior of this one. If that's the case, you may want to leverage an object or class for your action-type handlers instead a `switch` block. #avoid-switch-blocks

If not using React, it is dead simple to create a standard Event-Driven mediator that, beyond handling side effects, also gives us a system for leveraging CELs (Custom Event Loops). A mediator such as this can even be broken out into _Domain Heads_ for subdomains of our app, even using _Compositive Mediation_ and using Liskov Substitution so that lower domains don't know the difference between the Root Mediator (Application Head) and their own domain's mediator (Domain Head). This pattern scales indefinitely and is especially useful for complex lower domains where you need low level operations & data to aggregate before bubbling up higher-level data from the Child Mediator to that domain's Parent Mediator.



## Internationalization & Localization

### Myth
_You need an i18n/l10n library like FormatJS in order to internationalize a site or app_.

### Reason
A fully scalable Translator service can be built in 25-50 LOC.

### Conventions
Assuming a couple of minor conventions, Internationalization/Localization becomes very simple. Let's assume we have `locale.{lang}.json` files that look about like this.

#### `locale.en.json`
```json
{
    "PURCHASE:COMPLETE:MESSAGE": "Thank you for purchasing your new ${vehicle} ${locale['TAXON:DAY:TODAY']}!",
    "TAXON:VEHICLE:AUTO": "car",
    "TAXON:VEHICLE:MOTO": "motorcycle",
    "TAXON:DAY:TODAY": "today",
    "USER:SETTINGS:PRIVACY:BUTTON:SAVE": "Save",
    "USER:SETTINGS:PRIVACY:BUTTON:CANCEL": "Cancel",
    "USER:SETTINGS:PRIVACY:TAC": "${ltts.en}"
}
```

##### Conventions to Note
- **All** locale files use _fully-qualified_ translation keys — there is no nesting as this radically complicates our translation system. Preferably, this follows a reasonable _Domain-Driven Design_.
- Advanced translation values can use any convention of interpolation syntax.
- Interpolation tokens can use "_Taxa_", to automatically interpolate translation keys from the same locale file.
- Taxon translation keys should always start with the root qualifier of "`TAXON`".
- Translators can target specific keys or run the same operation over every process.

### Synopsis
In virtually 40 LOC, we can create a fully-scalable l10n system that performs the super simple mapping, employs a fallback system from injected environment variables (on `env`) to a `?lang` query parameter (which could also use `location.pathname.split('/').pop()`) to `navigator.language` to a `constructor` parameter, provides generic core _variable interpolation hooks_ including the use of **"TAXON" interpolation**, leverages specific translators that target specific translation keys for special operations only the app should know about such as which keys demand _Markdown Translations_, AKA LTTs (Large Text Translations). The `translators` system uses a specific flavor of the CoR pattern (_The Chain of Responsibility Pattern_) where, if you'd like to override a core translator, you can simply import it and call `translators.delete(name)` to remove it before adding your own. This does everything and more than any library out there that'll work until it doesn't. Others might allow nesting but that's simply a beartrap for the scalability of your code. The article coming up serves as a formal Gang of Four style Software Design Pattern specification for how to achieve this.



## CSS Modules and The CDC Pattern

### Myth
_You need a CSS Module framework to impose strict scoping on your CSS to restrict it to a single Trinity Module_.
> _Here, "Trinity Module" simply refers to a Frontend module composed of HTML, CSS, and JavaScript_.

### Reason
Following a simple pattern of **Domain-Driven Design & Modeling** within the CSS for your modules eliminates the need for CSS Modules, eliminates the need to decide between BEM, OOCSS & SMACSS, while striking a better balance of _CSS Specificity_ and providing more human readable `classNames` that loosely reflect that general Markup structure the component was intended to have.

### The Class Domain Chaining Pattern
The CDC Pattern consists of a parent element with a particular _domain_-identity as its chief token in the element `className`'s `DOMTokenList` _as the 2nd token in the `className`'s `DOMTokenList`_. The _first_ token in the DOMTOkenList takes that chief identifier of its parent's domain-identity. Optionally, an element can have a _third_ token in its className, used as a modifier class. For those familiar, this entire structure is similar to BEM — _Block Element Modifier_ — where the following are roughly equivalent.

- _Block_:      _Parent Domain_
- _Element_:    _Element Domain_
- _Modifier_:   _Modifier_

The key difference with CDC vs BEM is that the "Block" (in CDC, "Parent Domain") is used to loosely scope a nested element's Specificity to its parent, **drastically avoiding naming collisions** while striking a flexible but rigid enough balance of Specificity for each element. This creates a scoping strategy that is unique to each domain while allowing underlying elements the flexibility to closely resemble those from a different domain when necessary without the creation of the repeated selectors across any two domains. As an added benefit, this pattern naturally causes your HTML & CSS code to become more Human Readable.

#### Exceptions
- Root Element: the root element does not have a Parent Domain to reflect that is visible in the same code, so it may predict what that Parent Domain actually is; the most common Parent Domain for this case, the global header, is "`app`".
- The modifier namespace may leverage multiple tokens.

##### Modifiers
More than one _modifier_ class can be used. This may be due to necessarily more specific elements that have a similar sibling or when you simply want a larger composite className identifier to avoid conflicts.

Wrappers and other types of containers may be used, post-writing/structuring, that can break out of the main flow of chaining for any given element.

In extremely rare cases, when a selector's CSS Specificity happens to be more difficult to override, you can simply employ the standard CSS Specificity Hack of repeating one of the tokens that make up the selector's identity; e.g: `.app.header.header.main` (Specificity `4` instead of `3`). This tends to be very rare, however, when this is necessary.

### Synopsis
The CDC Pattern nudges the developer into striking an optimal CSS Specificity, loosely scoping elements to their parent, expressing selectors in Human Readable format, and saves you from having to come up with your own naming-conventions. Overall, this virtually **completely eliminates the need for using a CSS Module framework**. This is an easy transition for those already familiar with BEM, but with a much less cringy syntax. Similar to BEM, The CDC Pattern strikes an optimal balance of CSS Specificity between _avoiding selector collisions_ and _overriding defaults_. Lastly, reading the CSS file loosely conveys what the markup structure is, in a predictable and obvious way, without strongly coupling to markup structures that may likely change, other than the creation of wrappers; this radically enhances the developer's comprehension of the module, just by looking at the CSS file.



## A Pattern For Scalable Custom Frameworks

### Myth
_You need a frontend development framework for every UI you build_.

### Reason
Both Nicholas Zakas and Addy Osmani have come up with distinct approaches for defining, in their words, "Scalable Large Scale JavaScript Architectures". Whether you use a hybrid strategy between the two or not or put your own twist on any of it, there are a few aspects to each that are worth looking into. This goes for small, boutique sites and large ESAs alike. If you forgo writing your own Custom Elements, you can still start out with your own "poor man's framework" and scale it into something like what Zakas and Osmani have put forth.

Somewhat early on in my own career, I led a team of frontend developers at Oppenheimer Funds on a quest to clean up our frontend architecture for their enterprise scale marketing site. Architecture always exists but we had no _defined_ architecture. After gathering plenty of metrics for various static analysis, boomerang bugs and other things like coupling — even inventing our own analysis model, "CAMP" (Average Coupling Per Module) — I brought the issues to the frontend team's attention and from there the backend team to help us decide which direction to go. It was between my own flavor of a hybrid Zakas/Osmani architecture mixed with a more pure Zakas architecture. "Gen", my colleague, had Nicholas Zakas consult her team a few years before at another company, so we posed this new solution and put it up to a vote against React and Vue (v1) with the entire team of around a dozen engineers.

Our solution won and even 5 years after leaving the company I could check the console of that site for our namespace and they were still using it. That's some pretty good mileage and they may only have ditched it because it wasn't hip enough. That was not the first time I had written scalable custom frameworks for clients & companies who were very satisfied with it. A long time later, I came up with an even simpler pattern using `HTMLUnknownElement`s, which I've used for small intake websites — just for kicks.

### A Poor man's custom component framework

#### Basic
With just a couple of `function`s, we can have liftoff.

```typescript
class App {
    static tagName = 'app';
    static content = `<div>app<child></child></div>`;
}
```

```typescript
class Child {
    static tagName = 'child';
    static content = `<div>child</div>`;
}
```

```typescript
function bootstrap(Module) {
    const { tagName, content } = Module;
    const elements = this.getElementsByTagName(tagName);
    const instances = [ ...elements ].reduce(mount.bind(Module), []);
    
    return instances;
}
    
function mount(instances, element) {
    const { content } = this;
    const instance = new this(element);
    const collection = [ ...instances, instance ];
    
    element.innerHTML = content;
    collection.push( ...modules.map( bootstrap.bind(element) ) );
    
    return collection;
}
```

```typescript
const instances = [ App, Child ].map( bootstrap.bind(document) );
```

For its size, this _microframework_, if you will, packs plenty of punch — especially, if all you need it for is a small boutique site that'll never scale beyond 5 pages and, if it does, it's so simple and terse that nobody will have a problem translating it to another framework. We could also add some basic bells & whistles here that would make it much more pleasurable to work with — our own interpolation or something like Handlebars, automatic event-handler bindings, a `MutationObserver`, or types of property bindings. In the next section, we wrap the injected element in a _Sandbox_ (see Nicholas Zakas) to give us a bit more lift.


#### Using A _Sandbox_ (Nicholas Zakas)

##### Framework Core: `@core/core.ts`
```typescript
type Options = { target: HTMLElement } & any;

export class Core {  // Core IS the Sandbox
    static $components: Map<string, any> = new Map();
    private Component: any = Object;
    private tagName: string = '';
    public target: HTMLElement = document.createElement('div');  // use default div
    get dataset() { return this.target.dataset }
    get classList() { return this.target.classList }
    
    constructor(options: Options = {}) {
        var options = { ...this, ...options };
        const { Component, tagName, target } = options;
        
        this.Component = Component;
        this.tagName = tagName;
        this.target = target;
        
        return this;
    }
    
    static bootstrap(Component: any) {
        const { tagName } = Component;
        const $targets = document.getElementsByTagName(tagName);
        const targets = Array.prototype.slice.call($targets);
        const instances = this.mount(Component, ...targets);
        
        return this;
    }
    
    static mount(Component: any, target?: HTMLElement, ...more: HTMLElement[]) { // Tail-Call Optimized
        if (!target) return Core.$components.get(Component.tagName);  // early-return
        const { $components } = Core;
        const { tagName } = Component;
        const $ = new Core({ Component, tagName, target });  // sandbox instance
        const instance = new Component($);
        
        if ( !$components.has(tagName) ) $components.set(tagName, [ ]);
        $components.get(tagName).push(instance);
        
        if (more.length) return this.mount(Component, ...more);
        return $components.get(tagName);
    }
    
    on(type: string, handler: EventListenerOrEventListenerObject, capture: boolean = true) {
        const { target } = this;
        target.addEventListener(type, handler, capture);
        return this;
    }
    
    off(type: string, handler: EventListenerOrEventListenerObject, capture: boolean = true) {
        const { target } = this;
        target.removeEventListener(type, handler, capture);
        return this;
    }
    
    fire(type: string, data?: any) {  // dispatches on host component
        const { target } = this;
        const e = new CustomEvent(type, { detail: data });
        
        target.dispatchEvent(e);
        return this;
    }
    
    load(content: string) {  // loads innerHTML from string
        const { target } = this;
        target.innerHTML = content;
        return this;
    }
    
    style(styles: string) {  // injects styles in document head if not already existing
        if ( document.head.querySelector(`#${this.tagName}`) ) return this;
        const { tagName } = this;
        const { head } = document;
        const style = document.createElement('style');
        
        style.id = tagName;
        style.innerHTML = styles;
        head.appendChild(style);  // or append it inside of this.target
        
        return this;
    }
    
};
```

Notice that the static `mount` method takes advantage of Nicholas Zakas's "Sandbox" pattern by passing an instance of `Core` (`$`) into the component being bootstrapped, which _is_ the module's Sandbox. We could have added more utilities to the sandbox, such as an `interpolate` method, but this should suffice for bare minimum. In fact, we could even have the `load` method assume the use of a framework like Handlebars if we want. Here's what the usage might look like.

#### Using An Event-Driven Mediator (Addy Osmani)
If we want to incorporate a mediator (see _The Mediator Pattern_) for a cross-component Event-Bus, it is rather easy.

##### Mediator: `@core/utilities/patterns/behavioral/mediator.ts`
```typescript
const target = new EventTarget();  // use singleton instance

export class Mediator {
    
    dispatch(channel: string, data: = {}): this {
        const event = new MessageEvent(channel, { data });
        target.dispatchEvent(event);
        return this;
    }
    
    publish(channel: string, data?: any): this {
        if (channel in this) return this[channel](channel, data);
        return this.dispatch(channel, data);
    }
    
    subscribe(channel: string, handle: EventListenerOrEventListenerObject): this {
        target.addEventListener(channel, handle, true);
        return this;
    }
    
    unsubscribe(channel: string, handle: EventListenerOrEventListenerObject): this {
        target.removeEventListener(channel, handle, true);
        return this;
    }
    
};
```

##### Framework Core: `@core/core.ts`
```typescript

type Options = { target: HTMLElement } & any;

export class Core extends Mediator {  // Core IS the Sandbox
    ...
};
```

We demonstrated that there are scalable patterns for large scale frontend architecture and provided an example of what one flavor might look like (for inspiration). Remember, all these other frameworks started with someone else experimenting with their own patterns and then iterating on the ones that worked best. We are _not_ suggesting to reinvent the wheel at your company's expense but, when you go to build out that boutique site pro bono for your sister in law's salon, pay yourself off a little with experience and you might just invent the next best frontend development framework, SDK, or other patterns that will take your career to the next level. When you do that, you'll realize that oftentimes you don't really need a typical frontend development framework, you just need something that does what you need, including scaling.



## CSS Libraries Written As JavaScript Libraries

### Myth
_You need a JavaScript framework such as `@angular/material`, `@material-ui/*`, or otherwise_.

### Reason
80-100% of the purpose of your company's "Internal SDK" is aesthetical.

- It is largely a marketing ploy for a broader framework ecosystem to make it more "sticky" for Product Lock-In.
- The library was usually written by someone with a lack of frontend experience (CSS).
- The JavaScript library rarely bears proper CSS-selector hooks.
- It is majoritively to align your Design team's outcomes across the organization cohesively.
- CSS, especially at the time of this writing, accomplishes even most _behavioral_ aspects of your Design System goals.
- CSS prefers to use the GPU whereas JavaScript prefers the CPU to accomplish the same goal.
- CSS naturally provides a more declarative syntax than JavaScript can.
- Separation Of Concerns: mixing more data-logic in with your UX-logic makes your JavaScript less readable.
- Your Design System might change and, if mixed in with data-logic, makes your software more susceptible to error.
- Better Graceful Degradation.
- CSS will usually have a smaller code footprint.

#### Example: A Toggle Button
Oftentimes, you'll see some sort of "Toggle" system from a JavaScript library that should be a CSS library. This can be accomplished in several ways, generally speaking.

- `focus`
- `focus-within`
- _Stateful Buttons_
- HTML _Invoker Commands API_

##### A Basic Solution
```html
<span class="sdk popover">
    <button class="popover actuator">&bigstar;</button>
    <div class="popover envelope">...</div>
    <span class="popover deactuator">$times;</span>
</span>
```

```css
.sdk.popover {
    position: relative;
    &:focus-within {
        
        .popover.envelope {
            display: block;
        }
        
        .popover.deactuator {
            display: block;
        }
        
    }
    
    .popover.envelope {
        position: absolute;
        display: none;
        &[data-position="southeast"] {
            top: 100%;
            right: 0;
        }
    }
    
    .popover.deactuator {
        position: absolute;
        inset: 0;
        display: none;
    }
    
}
```
> _An inline-block container encapsulates a button that provides its width & height. The button naturally absorbs `focus` when selected. The `focus-within` selects the `envelope` to be displayed. At the same time, the `deactuator` follows suit and covers the display `actuator`. Because the deactuator is not a focusable element, clicking displaces focus, causing `focus-within` not to be a pseudo-class state any longer._

##### Stateful Buttons
In cases where your Design team needs multiple actions to maintain their state simultaneously, Stateful Buttons are an excellent option.

```html
<span class="stateful button">
    <input class="button receiver" type="checkbox" />
    <button class="button decoy">Press Me</button>
</span>
```

```css
.stateful.button {
    position: relative;
    
    .button.receiver {
        position: absolute;
        display: block;
        width: 100%;
        height: 100%;
        opacity: 0;
        z-index: 1;
    }
    
    .button.receiver:checked ~ button.decoy {
        background: green;
    }
    
}
```
> _We simply stretch an invisible `input[type="checkbox"]` over what the user only thinks they're interacting with. This works with `input[type="radio"]`, `input[type="file"]`, and any others you can imagine (even for invisible `select` boxes). This can be coupled with any number of other states you want to drive off of the `:checked` state of the hidden input, not limited to triggering dropdowns_.

> _NOTE: roughly the same thing can be achieved using `label[for="{id}"]` + `input[style="display: none"]`. Both depend on the preferences of you or your Design team, sometimes both. You can even use both strategies alongside CSS's `flex-direction: column-reverse` to ensure you always have your `input`s in the right order to leverage sibling selectors (`~` & `+`)_.

###### Main Benefits of The Stateful Button Pattern
- Higher/quicker Development Velocity.
- ADA Compliance: keyboard navigation is the most expensive to have to fix later.
- Power User empowerment.
- Testing: less to test when you piggyback off of native functionality.
- Making forms look nicer; you can use `input[type="radio"]` to get buttons to behave as a group instead of messy tracking of states using JavaScript.

##### A Note On Modern HTML
While they do not necessarily replace these broader patterns in the examples above, HTML has reduced the need to apply these patterns in specific cases through the introduction of the following APIs.
- The Popover API
- The Invoker Commands API

The Invoker Commands API can even replace what you might normally do with the Popover API and even, by listening to the `'command'` event on the target (modal, popover, etc), **receive custom commands**. Here's what that looks like.

###### Invoker Commands API
###### Standard
```html
<button commandfor="target" command="show-modal">Invoke</button>
<dialog id="target">
  <h1>A Modal</h1>
</dialog>
```

###### Custom Commands
Custom commands basically have only one requirement: _the command must begin with a double-dash (not unlike a CSS variable), `--`, in order for it to be picked up as a legitimate `CommandEvent`_.
```html
<button commandfor="target" command="--my-custom-command">Invoke</button>
<dialog id="target">
  <h1>A Modal</h1>
</dialog>
```
```javascript
const target = document.querySelector('#target');
target.addEventListener('command', handle, true);

function handle(e) {
    const { type, source, command } = e;
    const { tagName } = source;
    console.log(`@command`, type, tagName, command);  // > "@command" "command" "BUTTON" "--my-custom-command"
}
```

### Synopsis
We showed a couple of quick CSS patterns that have sky-high limitation, if any, while likely eliminating most-to-all of the need you thought a JavaScript library was satisfying. Once you master these basic concepts, you realize the importance of JavaScript's `activeElement` and can better help your Design team avoid costly mistakes that impede the engineering team. You'll start seeing that **the UI is not just a bunch of clicks & graphics, but a series of atomic _states_**. You can mix in more complex selectors, use Pseudo Elements, start using CSS for the things _it's best at_, and start using JavaScript for the things it is best at.



## Attribute Directives vs Element Directives

### Myth
_If your framework has no Attribute Directives out of the box, you need a library for it_.

### Reason
There are multiple ways to achieve "Directive" like functionality.

- Devise your own Attribute Directive system.
- Use a wrapper component (not recommended).
- Simply use another component (recommended).

### Attribute Directive System
While it's very easy to devise your own Attribute Directive system there are a few concerns you need to consider.

- Lifecycle Management: depending on which component framework you are using, you can encounter Race Conditions.
- Performance: you'll need some sort of DOM Node crawler that traces from a component's root, down its `children`, across siblings, and iterate on every `attribute` for each `Element`. This can be achieved performantly, however, it is not an easy feat. In tandem with the framework's Component Lifecycle, you may ask yourself if there is an easier way.

Here's what a simple implementation might look like, however.

```javascript
export const directives = new (class Registry extends Map {
    
    register(name, module) {
        this.set(name, { name, module });
        return this;
    }
    
    crawl(root, ...more) {
        if (!root) return;
        const { children, attributes } = root;
        // iterate attributes to find a match
        // if match, this.bootstrap(element, attr);
        this.crawl(...more);
        this.crawl(...children);
    }
    
    bootstrap(element, attr) {
        const { name } = attr;
        const { module } = this.get(name);
        module.call(module, element, attr);
    }
    
})();
```

```javascript
import { directive } from '@core/directive';

directive
    .register((directive, element, attr) => {})
    .register({
        call(directive, element, attr) {}
    })
    ;
```

```html
<Component some-directive="{permissions}" />
```

(OR)

```html
<Component directives="some-directive" data-some-directive="{permissions}" />
```

### `Element` Directives
The easiest way to accomplish your end goal for a directive is by simply defining a new component that creates an `Element` DOM `Node` and bootstraps behavior to it. This can be done in any component framework, if more convenient. Otherwise, this is roughly what it might look like as a Web Component.

```html
<div class="admin toolbar">
    ...
    <sdk-permission type="admin" permissions="${permissions}" />
</div>
```

```javascript
customElements.define('sdk-permission', class PermissionsElement extends HTMLElement {
    
    remove() {
        const { parentElement } = this;
        parentElement.remove();
    }
    
    ['handle:admin'](permissions) {
        if ( !permissions.has('admin-token') ) return this.remove();
    }
    
    connectedCallback() {
        const { attributes } = this;
        const { type, permissions } = attributes;
        const perms = new Set([ ...permissions.split(',') ]);
        const { [`handle:${type}`]: handle } = this;
        
        if (handle) handle.call(this, perms);
    }
    
});
```

This basic example, using a "permissions" directive, simply expects the directive is a direct descendant of the target element and hardcodes the handlers to the scope of the Custom Element. However, we have a lot of room to make this more flexible.

- The Strategy Pattern / The State Pattern: we can leverage these patterns however we like to delegate to other handlers.
  - The State Pattern could be used with a more generic `<sdk-directive>` element to swap entire classes, such as one for "permissions".
  - The Strategy Pattern in tandem with a `[strategy="presence|visibility|disablement]"` attribute can be used to define how the element should be treated; removed from the DOM, hidden, or disabled and grayed out. These can dovetail with CSS as well.
- Target Selectors: Element Directives can involve an attribute that specifies the following.
  - `[targets=".anything.with.any.type.of.selector"]`: Sibling elements' selectors to target.
  - `[omit="parent|siblings"]`: if present, indicates whether the parent vs siblings should be targeted.

### Synopsis
While writing your own custom Attribute Directive framework is a good option, it causes maintenance headaches. Element Directives are highly recommended unless the development framework you're using already bakes Attribute Frameworks into its Component Lifecycle considerations (such as Angular). Whether using native Web Components or another framework, these elements will automatically bootstrap and save you from having to write your own crawler which, generally, needs to be baked into the framework to be most performant. It also provides more room for configuration than a standard Attribute Directive would on a single element because a standard `Attr` instance virtually has only 1 datum of encapsulation while a single `Element` can have many `Attr` associated instances. Other libraries may also claim to hook into React's lifecycle (or another framework), however, you are likely better off writing an Element Directive that can scale to your organization's exact needs.



## Mock-Driven Development (MDD) &copy;

### Myths
- _You need a framework like Axios for HTTP Requests_.
- _You need a framework like Storybook for Playgrounds and Component Catalogs_.
- _You need a framework like Sentry or LogRocket for logging & telemetry_.

### Reason
All of these disrupt Mock Driven Development practices if coupling to them directly.

### What Is MDD?
MDD is the strategy of employing heavy use of mocks in all approaches of software development from the outset. The benefits are numerous and solve many of the problems that plague us on the frontend.

#### Benefits of MDD
- Development Velocity: tighter feedback loops while building, running, and writing tests.
  - Cross-network calls: fetching data is instantaneous.
  - Control over data: when you have control over what the data looks like, you require fewer feedback loops to write code.
  - Tests: Unit and Functional Tests reuse the same data as your catalog/playground (see below).
- Fault Tolerance: running the UI against mocks before real data discovers hidden anomalies in your code you were unaware of.
  - API outages: backend teams can work in parallel, making breaking changes, without impacting the UI until you go live (locally).
  - Network outages: ISP outages, VPNs, and other problems do not lower development velocity.
  - Airplane Mode: developers traveling on airplane need not pull the company card out for onboard wifi service.
- Quality Assurance: QA Engineers are happier when they can spoof operations in different environments.
  - State Loaders: Console APIs can be built for different environments so QAEs can instantly jump to specific user flows & states.
- Component Catalogs/Playgrounds: developing in a playground makes your code more portable when running it live (locally).
  - Stakeholder Transparency: providing a Component Catalog to your Product or Design team leads to cross-team productivity. 
  - Debugging: debugging in a playground/catalog allows you to tweak mimic production issues easier.
- Testing: mock data can be reused across different tests and different types of tests that run faster.
  - Unit Tests: Unit Tests can use the same data from your catalog.
  - Functional Tests: Fn Tests run as fast as possible and so can replace many of your heavy, cumbersome Unit Tests.
  - Smoke Tests: Smoke Test all of your components from a single component catalog.
  - Flakiness: MDD narrows test flakiness down to those only related to differences in environment.
- Telemetry: easily implement flexible telemetry & logging across any environment.
  - XHR: interjecting on network operations reduces side effects collected in telemetry services.
  - Logging: by always import and swapping out the `console` object per env eliminates the need to upgrade logging subscriptions.
- CI/CD: faster CI systems can be build without infrastructure to setup tokens, containers, and other configurations.
  - Pull Request Gating: quickly reject PRs that don't pass a test.
- Demo-Safe Instances: Developers, Product Owners and Sales personnel can safely demo instances that do not humiliate the company.

As you can see, we overcome _many_ of the common plagues we as frontend developers experience — portability, entropy, fault tolerance, ... the list is massive. Here's roughly how to employ this approach.


### A Word On The Abstract Factory Pattern
As you may notice in the article coming up that we are beginning to [loosely] implement **The Abstract Factory Pattern**. The Abstract Factory Pattern does what _The Factory Method Pattern_ does but on a larger scale. That is, it uses a "Factory" that provides _Families_ of modules as opposed to a distinctly different _individual_ module. While each _file_ loosely implements The Factory Method Pattern, as a whole, our app receives an entire "family" of modules by simply importing each one as necessary.

### Synopsis
We demonstrated why you generally don't want to spring for a framework that does everything `fetch` already can. It is tougher to normalize against a library that you do not control, know little to nothing about its internal workings, or may change at the whim of personnel not on your team. Wrapping your telemetry service and importing your `console` at the beginning of a project can save you from expensive subscription price increases when you cannot afford to refactor unwrapped invocations all over your codebase. Once you have your 'Environment Factory' setup, you can easily build out something like a _HashRouter_ that uses CSS `:target` for showing and hiding elements in a _very_ plain Playground that speeds up development and acts as a Component Catalog which stakeholders can view for feedback, testing, technical User Story details, and refinement. Ultimately, the more you employ these techniques across a Mock Driven Development approach, the more benefits you'll stack up from the list in this subject's opening.



## Feature Flags

### Myth
_You need a Feature Flag framework or subscription service for gating features in production_.

### Reason
Most of what you want out of a Feature Flag framework + service can be accomplished by _Environment Flags_, which are virtually free and unblock bottlenecks in development & release flows.

We can likely get a lot of mileage out of an approach like this before we need something with a lot more configurability, if at all. If fact, we can likely even delegate more configuration to a simple JSON file and carry this approach much further forward.

### Driving Traffic By URL
Again, before we necessarily reach for anything serverside and asynchronous, it depends on our needs. If all we need to drive A/B variants is coming from emails. We can set up "_Aux Routes_" in our frontend.

#### Aux Routes
And Aux Route, or _Auxiliary Route_, is basically any route that starts at `{origin}/aux`. Aux Routes are intended for external routes coming from _outside_ of the frontend hosting it. This is typically for visitors arriving from other apps or sites in your ecosystem or, more importantly here, from email links.

Driving your A/B variants from emails or similar may be as simple as navigating the user to `{origin}/aux/campaigns/{campaignId}` (or using a URL Search parameter).

### Synopsis
Having said all this, there is some point where you may want to get a server or 3rd-party service involved. The demand for such may make plenty of sense at some point but, if all you need is for the Product Team to manipulate the JSON config through a GUI and commit it to the repository, well, you might even find a clever solution for that. Point is, you can get plenty of mileage out of pure fontend patterns and solutions that, depending on budgets & salaries, may get you where you need to go and save your team or company from subscription service prices that could be unnecessary. If all you need is basic gating of features for development flow, bottlenecking, and Release Candidates — all you likely need are simple Environment Flags, _not_ an entire Feature Flag system with an invoice attached.



## Testing Frameworks

### Myth
_You need a testing framework for testing modules written in the framework you're using_.

### Reason
Tests should be lightweight and not test the framework's lifecycle boundaries anyway; the framework author already wrote those tests.

### Lightweight Tests
Tests should be lightweight and easy enough to write that developers are not discouraged from writing them. In fact, the heaviest Unit Tests I've seen were testing things that either already exist or should only exist in a Functional Test. Oftentimes, you cannot fully test a component because, as a good thing, it was leveraging CSS as much as possible. This is where Functional Tests come in. Otherwise, I see Unit Tests that use the development framework's own test utilities so that all component lifecycle boundaries can be tested; **these tests already exist in that framework's repository!** We ought to be able to trust that lifecycle hooks work will always work in the framework and discard those concerns from our own tests. The biggest culprit I tend to see wasting people's time is Angular, but they almost all do it.

#### Rules Of Thumb For Testing
- Keep them lightweight.
- Never test lifecycle boundaries.
- Unit Tests for all basic IO operations and states driven by them.
- Functional Tests for anything that mimics a User Action, especially ones that are CSS based.

#### Example
Say we are using Lit. Lit requires a `render` method that returns a template. If we were to test a DOM Element we wrote with Lit, it should necessarily look more like the following.

##### `@app/children/**/*.test.ts`
```typescript
import { render } from 'lit';
import { MyElement } from './*.element';

describe(`My Element`, () => {
    
    it(`should have default state X reflected in its HTML`, () => {
        const instance = new MyElement();
        const html = render(instance);  // calls instance.render() among other things
        const event = new MouseEvent('click');
        const spy = spyOn(instance, 'handleClick');
        
        instance.innerHTML = html;
        instance.handleEvent(event);
        
        expect(spy).toHaveBeenCalledWith(event);
        expect(instance.shadowRoot.querySelector('.my.input').checked).toEqual(instance.checked);
        expect(instance.checked).toEqual(true);
    });
    
});
```
> _Assumes a click event ultimately changes the state of the component, thus effecting what its next render will be._

##### Antipattern: `@app/children/**/*.test.ts`
```typescript
import { superDooperRenderLifecycleHarness } from 'productLockIn';
import { MyElement } from './*.element';

describe(`My Element`, () => {
    
    it(`should have default state X reflected in its HTML`, () => {
        const api = superDooperRenderLifecycleHarness(MyElement);
        const event = new MouseEvent('click');
        const spy = spyOn(instance, 'willUpdate');
        
        api.stageClickEvent();
        
        expect(spy).toHaveBeenCalledWith( api.mockClickEventObject() );
        expect( api.magicallyGetInputStateSomehow() ).toBe(true);
    });
    
});
```
> _Assumes the framework will do all sorts of magic behind the scenes for us and diminishes transparency while we make sure `willUpdate`, a framework-specific lifecycle method, is always called whenever the framework decides it should be._

### Synopsis
This is about as far into the weeds of the DOM as we probably want to get in a Unit Test and, instead, let our Fn Tests pick up the more DOM/User heavy testing. In our Unit Tests, however, we want to just keep invoking methods, checking on the component's state from an encapsulation standpoint and keep checking to see what the HTML output is. We may leverage `Element.prototype.dataset`, `Element.prototype.classList`, or other properties of its subtree, but nothing too complex. Save the complexity for the Functional Tests instead. We don't need heavier apparatus around testing that will ensure the framework works as we ought to be able to assume. That is just more "stickiness" technology providers have shoehorned into your workflow for Product Lock-In.
